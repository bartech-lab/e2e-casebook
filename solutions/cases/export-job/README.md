# Case 4: export job

## Feature

**Export board as CSV** starts a background job: ten steps of 500 ms each. The page polls once a
second while a job runs and stops polling when none does. A running job can be cancelled; a failed
or cancelled job can be retried, which starts a new job that names the old one; a finished job
offers **Download CSV**.

What can go wrong: cancel marks the job cancelled but it keeps working; retry reuses or overwrites
the old job; the page stops polling and freezes mid-progress; the page never stops polling; or
Download appears before the file exists.

## Approaches

| # | Spec | What it does |
|---|---|---|
| 1 | [`1-real-time`](1-real-time.spec.ts) | Real timing: start, wait for Done, download, read the CSV. |
| 2 | [`2-fast-steps-hook`](2-fast-steps-hook.spec.ts) | The fault hook shortens steps and makes a run fail at step 3; tests retry and cancel through the page. |
| 3 | [`3-mocked-api`](3-mocked-api.spec.ts) | `page.route` plays a scripted job (30%, 60%, failed) and counts the page's polls. |
| 4 | [`4-api-only`](4-api-only.spec.ts) | No browser: fail, retry, cancel through the API. |

## Trade-offs

- **1 Real time.** Proves the whole path, download included, with nothing faked. It is the slowest,
  and it only walks the happy path, so it misses four of five.
- **2 Fast steps through the hook.** Catches the most: the hook makes failure and cancel reachable
  in seconds. Its cancel test has to wait a fixed 900 ms to show that progress does *not* move;
  proving absence costs a wait. Needs a test-only API in the product.
- **3 Mocked API.** The only approach that notices endless polling, because it owns the responses
  and can count requests. It cannot see any server bug.
- **4 API only.** The fastest check of the job rules, blind to everything on the page.

Polling bugs live in the page and job bugs live in the server; no single layer sees both. Pair 2
with 3, or 2 with a poll-counting assertion of its own.
