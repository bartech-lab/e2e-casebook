# Case 3: optimistic moves

## Feature

On the board, a card moves to its new column at once, before the server answers. When the last
pending move of a card settles, the page refetches that card and shows what the server has. A
failed move shows one error.

What can go wrong: a failed move leaves the card in the wrong column; rollback restores the status
the card had when it was clicked, although a later move of the same card succeeded; a rollback
restores the whole board and undoes another card's successful move; the error shows twice; or the
server never stores the move, which an optimistic page hides until a reload.

## Approaches

| # | Spec | What it does |
|---|---|---|
| 1 | [`1-happy-path`](1-happy-path.spec.ts) | Move a card, check the column, reload, check again. |
| 2 | [`2-route-fail`](2-route-fail.spec.ts) | `page.route` fails the `PATCH`; the card must go back, with one error. |
| 3 | [`3-fault-hook-out-of-order`](3-fault-hook-out-of-order.spec.ts) | The fault hook fails one card's move slowly (800 ms) while other moves succeed fast. Two tests: two cards, and the same card moved twice. |
| 4 | [`4-model-based`](4-model-based.spec.ts) | fast-check generates 8 random runs of up to 3 batches of overlapping moves, each move a fast success, slow success, or slow failure through the fault hook (fixed seed); after each batch it checks the server, the columns, and the error count against a model. |

Approach 3 is the slowest because it waits out the 800 ms delay.

## Trade-offs

- **1 Happy path.** Cheap, and the reload makes it the only page-level check that the server
  stored the move. It never sees a failure, so it misses every rollback bug.
- **2 Route fail.** Fast and needs no product hook. One request failing alone is the easy case:
  the naive rollbacks look correct when nothing else is in flight. And because the request never
  reaches the server, it cannot notice a server that ignores moves.
- **3 Fault hook.** The only approach that finds the ordering bugs, because the hook can make a
  failure arrive *after* a later success. It needs a test-only fault API in the product and costs
  the injected delay.
- **4 Model-based.** Catches all five without a hand-picked race, at about 27 s per run, ten
  times approach 3. Writing the model found its own mistake first: two equally slow moves of one
  card may reach the server in either order (likely because `onMutate` awaits `cancelQueries`
  before sending; not traced), so
  the model accepts either target and then requires the page to show what the server kept.

The rollback bugs that matter only appear with two writes in flight. A suite that never overlaps
requests will pass all three of those planted bugs.
