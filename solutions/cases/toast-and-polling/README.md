# Case 10: a toast and a page that is never idle

## Feature

**Save settings** sends `PUT /api/s/:id/settings` and, once the server answers, shows the toast
"Settings saved" (`role="status"`) for 2 seconds. A failed save shows "Could not save settings".
Every sandbox page also keeps a long-polling request open for the notifications badge, so the
network is never idle.

What can go wrong: the toast appears before the server confirms (and also on failure); it never
appears; it disappears too fast to read; the save sends stale values while the toast still shows.

## Approaches

| # | Spec | What it does |
|---|---|---|
| 1 | [`1-networkidle`](1-networkidle.spec.ts) | `@naive`. Waits for `networkidle` before and after saving. |
| 2 | [`2-web-first`](2-web-first.spec.ts) | Web-first assertions: the toast appears and the value is stored; a failed save shows an error and no toast. |
| 3 | [`3-clock`](3-clock.spec.ts) | `page.clock`: the toast is still there at 1.9 s and gone at 2.1 s of page time. |
| 4 | [`4-side-effect-only`](4-side-effect-only.spec.ts) | Polls the settings API until the value is stored; ignores the toast. |
| 5 | [`5-absence-at-the-moment`](5-absence-at-the-moment.spec.ts) | Checks once, with `count()`, that no toast exists while a 1 s delayed save is in flight and at the moment a failed save shows its error. |

## Evidence

Approach 1 times out after 5 s on every run on the healthy build: the long poll keeps a request
open, so `networkidle` never arrives. It is excluded from the matrix below.

Approaches 2 to 4 mostly miss the early toast. Approach 2's verdict drifts with rendering speed:
it caught the early toast in 0 of 10 runs when first scored, 1 of 10 on app c2ef129, and 3 to 6 of 10
after the 2026-10-22 restyle (three batches). A check that sometimes catches a bug is a race, not a
test. Approach 2's failed-save test should have caught it every time,
because the toast does appear on the failed save. But `toHaveCount(0)` is a web-first assertion
and retries for up to 5 s, so it waits out the 2 s toast and passes. An absence assertion that
retries proves only that the thing is gone eventually.

Approach 5's catch of the 200 ms toast is a timing accident: the in-flight test's `toBeVisible`
polls at growing intervals and missed the short toast in all 10 runs.
A faster machine or a different delay could let it pass, so approach 3 is the real check for
duration.

A first draft of approach 5 used `toHaveCount(0, { timeout: 0 })`. In Playwright, `timeout: 0`
means no timeout, not "check once", so it waited for the toast to go and passed the early toast.
Watching each test fail on a planted bug exposed this.

## Trade-offs

- **1 `networkidle`.** Fails on any page with a long poll, a socket, or analytics beacons. With
  a short poll it can pass by luck, because gaps between requests exceed the 500 ms idle window.
- **2 Web-first.** Fast and catches a missing toast and a wrong save. Web-first retrying hides a
  toast that is too short-lived or that should never have appeared.
- **3 Clock.** The only approach that checks the toast's duration, without waiting 2 real seconds.
  It checks only the success path.
- **4 Side effect only.** Proves the data and nothing on the page.

- **5 Absence at the moment.** The only approach that proves the toast waits for the server. It
  needs a moment to check against (a delayed response, an error already on screen), and a
  one-shot `count()`, which gives up the auto-waiting that keeps the other checks stable.

Wait on the thing you assert, never on the network. To prove something did *not* appear, check
once at the moment it would have shown, or control time with the clock. A retrying absence check
waits the bug out, and `timeout: 0` retries forever.
