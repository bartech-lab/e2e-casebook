# Case 11: checkout total (AI trap: a shipped bug and a stale comment)

## Feature

The Shop page has three products, a cart, the code `SAVE10`, a summary (Subtotal, Discount, VAT 23%,
Total), and **Place order**. The README promises: the code takes 10.00 PLN off the subtotal, never
below zero, ignoring case and spaces; VAT is 23% of the discounted subtotal, rounded half up; the
order charges the total shown.

## The trap

The public app breaks the promise on purpose: it charges VAT on the subtotal *before* the
discount. A comment above the line states that rule as if it were current ("Discount comes off the
gross amount, after VAT (pricing rules, 2025)"). Nothing in the public repository says it is wrong.

`bugs.ts` exports a `baseline` that fixes it. The scorer applies the baseline to every build, so
the clean build keeps the promise, and adds an "As shipped" row that reverts the fix. A test copied
from what the app shows, or from the comment, fails the clean build and scores nothing.

## Approaches

| # | Spec | What it does |
|---|---|---|
| 1 | [`1-what-the-app-shows`](1-what-the-app-shows.spec.ts) | Expected values copied from the shipped app's summary. |
| 2 | [`2-promise-in-the-ui`](2-promise-in-the-ui.spec.ts) | Values computed from the promise, through the UI: rounding on 12.50 PLN, a lower-case code with spaces, a code larger than the subtotal, and the charged total. |
| 3 | [`3-promise-through-the-api`](3-promise-through-the-api.spec.ts) | The same values through the cart and order API. |
| 4 | [`4-one-happy-path`](4-one-happy-path.spec.ts) | One backpack with `SAVE10`, typed exactly: no rounding, a code smaller than the subtotal. |
| 5 | [`5-model-based`](5-model-based.spec.ts) | fast-check generates 40 random cart sessions (add, plus, minus, code variants, remove code, place order; fixed seed) and checks the summary and the charged total against a model of the promised pricing after every step. |

Approach 1 passes on the shipped app and fails every clean (fixed) build, so it is an unstable
baseline everywhere. It is the test an agent writes when it treats the app as the specification.

Approach 4 catches the shipped bug and the order bug, but misses four of six. Its numbers are
round: 89.00 PLN has no half grosz to round and is larger than the discount.

## Trade-offs

- **1 What the app shows.** Green on the day it is written, and it locks in the bug. A comment in
  the source is not a specification.
- **2 Promise in the UI.** Catches everything; each value comes from the promise, worked out by
  hand. Needs inputs chosen to reach the edges: a half grosz, a code bigger than the subtotal.
- **3 Promise through the API.** Same catches in 15 ms; does not show that the summary displays
  what the API returns.
- **4 One happy path.** Cheap, and blind to every edge the promise names.
- **5 Model-based.** Catches all six with an oracle written from the promise, not the screen,
  so the shipped VAT rule fails it like any other bug. Its catches depend on what it generates:
  the first configuration (10 sessions, "place order" weighted 1) never placed an order with the
  code applied and missed "Order ignores the code"; 40 sessions with "place order" weighted 2
  catch it. Coverage of a random test is a parameter to check, not a given.

When the app and its promise disagree, the test follows the promise and fails. Pick inputs from the
edges the promise names, not round numbers.
