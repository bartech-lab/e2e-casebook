# Case 6: due dates, time zones, and DST

## Feature

Cards can have a due date (`YYYY-MM-DD`, no time). The board shows **Overdue**, **Due today**,
**Due tomorrow**, or **Due in N days**, counted in the visitor's local calendar days, and refreshes
the badge every minute so an open board turns over at midnight.

What can go wrong: "today" is taken in UTC, so a late-evening visitor west of Greenwich sees
tomorrow's labels; days are counted as `ms / 86,400,000` between local midnights, so a 23-hour DST
day loses a day; the badge is computed once and never updates.

## Approaches

| # | Spec | What it does |
|---|---|---|
| 1 | [`1-real-clock`](1-real-clock.spec.ts) | Real clock and the machine's time zone; seeds today, tomorrow, and yesterday. |
| 2 | [`2-clock-and-timezone`](2-clock-and-timezone.spec.ts) | `timezoneId` plus `page.clock`: 23:30 in Los Angeles, a midnight turnover, and the Warsaw spring DST weekend. |
| 3 | [`3-init-script-date`](3-init-script-date.spec.ts) | `timezoneId` plus an init script that replaces `Date` with a frozen one. |

## Trade-offs

- **1 Real clock.** Easy to read, and it passes or fails depending on when and where it runs. It
  would catch the UTC bug only if run between local midnight and the UTC offset, and the DST bug
  only on the two weekends a year when a change is near.
- **2 Clock and time zone.** Places the test at the exact boundary that matters and advances time
  on demand, so the midnight turnover takes no real wait. The only approach that catches all three.
- **3 Frozen `Date`.** Reaches the same boundaries without the clock API, but timers still run in
  real time and `Date` never moves, so it cannot test anything that changes over time. A
  hand-rolled `Date` replacement is also easy to get subtly wrong.

Date bugs live at boundaries the real clock rarely visits. Choose the moment and the zone in the
test; 2 does both and also controls timers.
