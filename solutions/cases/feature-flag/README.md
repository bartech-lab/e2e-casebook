# Case 5: feature flag

## Feature

New cards are created with one of two variants: an **inline** form ("New card title", **Add card**)
or a **dialog** (**New card**, then Title, Description, Due date, **Create**). A visitor is assigned
one at random and keeps it in localStorage; `?variant=` overrides it; a sandbox can pin one variant
for everybody through the flags hook.

What can go wrong: one variant silently stops working while the other is fine; the pin is ignored;
the stored assignment is forgotten, so a visitor sees a different variant on every visit.

## Approaches

| # | Spec | What it does |
|---|---|---|
| 1 | [`1-whatever-you-get`](1-whatever-you-get.spec.ts) | Detects the variant on the page and drives whichever appears. |
| 2 | [`2-pin-with-hook`](2-pin-with-hook.spec.ts) | Pins each variant through `POST /__test__/s/:id/flags`, one test per variant. |
| 3 | [`3-pin-in-browser`](3-pin-in-browser.spec.ts) | Writes the assignment into localStorage with an init script, one test per variant. |
| 4 | [`4-pin-one-only`](4-pin-one-only.spec.ts) | Pins inline only, the variant "most users see". |
| 5 | [`5-pin-against-the-fallback`](5-pin-against-the-fallback.spec.ts) | Like 2 and 3, but the fallback always disagrees: the server pin is checked with the opposite variant stored, and the stored variant with the `draw` hook set to the opposite. |

The flaky counts vary between scoring runs: the first full scoring had 8/10, 5/10, 6/10, 8/10, and
7/10 in the same cells. Only approach 5's column is stable.

The first hand-run matrix (one run per bug) showed approach 1 as "missed" everywhere and the pin
bugs as "caught". Ten runs show both were luck. A visitor's variant is random, so a broken
variant fails approach 1 only when the visitor draws it. And when the pin or the stored
assignment is ignored, the page falls back to a random variant, which matches the pinned one
often enough to pass: 2 and 3 run two tests each, so they fail about 3 runs in 4; 4 runs one test
and fails about 1 in 2. Expected rates, consistent with these counts but not measured precisely.

A pin test only proves the pin when the fallback would show the other variant. Approach 5 does
that and is the only one that catches all four bugs in every run.

## Trade-offs

- **1 Whatever you get.** No setup, and it tests a coin flip: a broken variant fails it only when
  the visitor draws that variant, which reads as a flaky test. Branching on what the page shows
  (`if visible ... else ...`) hides the variant under test.
- **2 Pin with the hook.** Tests both variants on purpose. It catches a broken pin only when the
  random fallback differs from the pin. It needs a test-only API, and it never exercises the
  visitor's own assignment.
- **3 Pin in the browser.** No product hook needed; it checks the client-side assignment path.
  It relies on a storage key the app treats as private, and it cannot see a server pin bug.
- **4 One variant only.** Cheapest, and as blind as 1 for the other variant.
- **5 Pin against the fallback.** Deterministic, and catches all four. It needs two test-only
  hooks: the pin and the `draw` seed. An earlier version forced `Math.random` instead, which tied
  the test to how the app draws (`Math.random() < 0.5`); the `draw` hook (added 2026-10-20)
  removed that coupling.

A flagged feature needs one test per variant, pinned explicitly, with the fallback set to disagree
with the pin (5). Without that, a broken pin fails only some runs and reads as a flaky test.
