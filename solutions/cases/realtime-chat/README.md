# Case 1: two-user realtime chat

## Feature

A chat room inside a sandbox. Sending is a `POST`; every open page in the sandbox gets the message
over a WebSocket. Each message has a server-assigned `seq`. A page that reconnects asks for
`since=<last seq>` and the server replays what it missed. The page shows the connection state in
`data-testid="connection"` (`connecting`, `open`, `closed`).

What can go wrong: the message never reaches the other user, the sender sees it twice (once from
the `POST` response, once from the broadcast), messages render out of order, and messages sent while
a page is offline are lost after it reconnects.

## Approaches

| # | Spec | What it does |
|---|---|---|
| 1 | [`1-one-page`](1-one-page.spec.ts) | One page sends and checks its own list. |
| 2 | [`2-two-contexts`](2-two-contexts.spec.ts) | Two browser contexts, two users, each checks the other's messages. |
| 3 | [`3-api-as-other-user`](3-api-as-other-user.spec.ts) | One page; the second user is the HTTP API. |
| 4 | [`4-reconnect-fault-hook`](4-reconnect-fault-hook.spec.ts) | Two contexts; the test hook drops one socket; the page clock holds the reconnect until the other user has sent. |
| 5 | [`5-mocked-websocket`](5-mocked-websocket.spec.ts) | `page.routeWebSocket` replaces the server and pushes crafted messages. |

The `reset` push row is not a bug a user can see: the server closes the socket with code 4000 right after the push, and
the client clears its list on that close too. The mock caught a protocol detail, not a behaviour.

## Found only on the deployed demo (2026-10-19)

Running the same specs against the public Render deploy exposed two bugs the local runs never showed:

- **Close frames are lost behind the proxy.** The browser got the in-band `reset` message at once,
  but the close only 20 s later, as code 1006 with the app's code gone. A dropped socket went
  unnoticed for about 20 s. Fixed in the app: in-band `reset`/`gone`, a 5 s server ping, and a 12 s
  client silence watchdog. Approach 4 now advances the page clock in 250 ms steps until the page
  shows `closed`, so it works whether the close frame arrives or not.
- **History request vs. live pushes.** The client read its cache before awaiting the history fetch,
  so pushes that arrived during the request were overwritten. Locally the fetch is too fast;
  on Render, approach 5 (mocked WebSocket, real HTTP) failed 4 of 6 runs. Fixed in the app.

Approach 5 was the only one to catch the second bug: a mock is weak on the server, but it can push
at a moment real traffic rarely hits.

## Trade-offs

- **1 One page.** Cheapest, and it reads like the user story. It cannot see delivery to anyone
  else: the sender's own message comes back in the `POST` response, so it passes with broadcasting
  switched off. Choose it only as a smoke test.
- **2 Two contexts.** Proves what users see on both sides. It costs a second browser context and
  still never exercises reconnect or ordering under load. A good default for "it works for two people".
- **3 API as the other user.** As fast as a mock but talks to the real server, so it proves
  delivery to a browser. It does not drive the sender's UI, so it misses client bugs on the sending
  side (duplicates). Choose it when the sender's UI is covered elsewhere.
- **4 Fault hook.** The only approach that proves recovery: reconnect and replay. It needs a
  test-only endpoint in the product, and the reconnect timer must be held with `page.clock`;
  without it the page sometimes reconnects before the missed messages are sent, and the test
  passes even with replay broken. The slowest of the five.
- **5 Mocked WebSocket.** Deterministic and fast, and the only approach that can stage
  out-of-order and duplicate pushes on demand. It tests the client against a server the test
  invented, so it misses every server bug and can fail on details the real server makes harmless.

No single approach catches every planted bug. Approaches 2, 4 and 5 together catch all six.
